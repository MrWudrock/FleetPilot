**Версия:** 1.0  
**Дата:** 17.07.2026  
**Статус:** Готово к согласованию (пилот + продукт)

**Метод составления:** подход Зерокодер  + текущие артефакты FleetPilot (PRD, Product Plan, архитектура, Sprint 7 Permit API)

> **Как читать этот документ.**  
> ТЗ на **человеческом языке**: что продукт делает сейчас, для кого, какие сценарии обязательны, что сознательно откладываем.  
> Не описываем «кнопка справа сверху». Визуал — на этапе дизайна / wireframes.

## 0. Принципы, по которым собрано это ТЗ

Из рекомендаций по составлению ТЗ от Зерокодер применили к FleetPilot:

| Принцип | Как применили здесь |
|---------|---------------------|
| Функция должна **зарабатывать сейчас** или быть **необходимой** для работы системы | В MVP оставили то, без чего нет пилота и оплаты: телематика, заявки, Permit, Fuel, ROI. ML-маршруты, Playwright Росдор, полный 1С API — v2 |
| Не раздувать ТЗ «всем, что хотелось бы» | PRD (20–50 ТС, 4+ агента, ЮKassa, 3 GPS) сужен до **пилотного контура** |
| Не изобретать велосипед | Auth: **email + пароль** (уже в API). HITL вместо «чёрного ящика ИИ» |
| ТЗ 5–10 стр. понятным языком | Этот файл — единый контрактный срез; PRD/архитектура — детальные приложения |
| Смотреть на аналоги и proven-паттерны | Надстройка над Wialon/TMS (как рынок уже привык), не замена; ROI dashboard как GTM-якорь |
| Сначала главный сценарий, остальное вырезать | Главный сценарий пилота: **заявка → ТС на карте → разрешение/топливо → ₽ экономии** |

**Источники проекта:** `docs/fleet-ai/PRD.md`, `notion/PRODUCT-PLAN.md`, `PM-PLAYBOOK.md`, `ROSDORMONITORING-INTEGRATION.md`, `apps/` (реализация).

## 1. Что строим (кратко)

### 1.1 Product name

**FleetPilot** — B2B SaaS для управления автопарком в РФ.

### 1.2 One-liner

Единый кабинет поверх уже установленных GPS/TMS: где машины, что с заявками, нужно ли спецразрешение, где теряется топливо и сколько автопарк экономит в рублях.

### 1.3 Задача MVP (бизнес)

Проверить, что оператор автопарка **готов платить** за кабинет, если за 6–8 недель видит:

1. живые машины с телематики на карте;
2. заявки из своей TMS;
3. ускорение работы со спецразрешениями (негабарит);
4. алерты по топливу и понятный ROI.

### 1.4 Пилотный клиент (референс для MVP)

| Параметр | Значение |
|----------|----------|
| Автопарк | **6 ТС** |
| GPS | **Wialon Local** |
| TMS | **ТрансМенеджер** |
| Разрешения | **Росдормониторинг** |
| Учёт | **1С** (в MVP — CSV-сверка, не полный API) |

> MVP продукта = функциональность, достаточная для такого пилота + демо-организация. Масштаб 20–50 ТС — после успешной приёмки пилота (тариф Pro).

## 2. Для кого и какую боль закрываем

### 2.1 Пользователи (роли)

| Роль | Кто это | Что делает в MVP |
|------|---------|------------------|
| **Admin** | Владелец / IT | Регистрация org, пользователи, подключение интеграций |
| **Dispatcher** | Главный диспетчер | Заявки, карта, Permit (анализ + утверждение), алерты |
| **Fleet Manager** | Руководитель автопарка | ROI, топливо, utilization, P&L по машинам |
| **Viewer** | Наблюдатель | Только чтение (отчёты) |

### 2.2 Problem statement

Данные размазаны по Wialon, TMS, Росдор и 1С. Диспетчер вручную переносит заявки и габариты. Спецразрешения занимают часы. Нет одного места, где видно: машина работает, сколько стоит и сколько зарабатывает.

### 2.3 Почему сейчас

GPS/TMS уже стоят — нужен слой поверх них. Штрафы и негабарит давят. Permit API (Sprint 7) уже готов к пилоту. Founding-оффер ₽49K/мес.

## 3. Что входит в MVP (Must) — функции и задачи

Формат: **задача пользователя → что делает система → критерий приёмки**.

### M1. Регистрация компании и вход

**Задача:** админ создаёт организацию и входит в кабинет.

**Система:**
- регистрация / логин по **email + пароль**;
- роли RBAC (admin, dispatcher, fleet_manager, viewer);
- demo-организация для продаж (`demo@fleetpilot.ru`).

**Приёмка:**
- [ ] Успешный signup + login, JWT-сессия
- [ ] Пользователь без роли не видит чужой org (multi-tenant)
- [ ] Неверный пароль → понятная ошибка

**Статус:** ✅ реализовано (auth API + web login).

---

### M2. Автопарк: карточки машин

**Задача:** админ заводит 6 (и более) ТС: госномер, марка, модель, VIN/класс, привязка к внешнему ID телематики.

**Система:**
- CRUD машин в org;
- поле `external_ids` для Wialon unit_id;
- статусы: active / inactive / maintenance.

**Приёмка:**
- [ ] 6 машин созданы и видны в списке
- [ ] Госномер уникален в рамках org
- [ ] Машину можно связать с unit из Wialon

**Статус:** ✅ модели + seed; UI списка — частично (довести в web).

---

### M3. Интеграция телематики Tier 1 (Wialon)

**Задача:** админ подключает Wialon Local / Hosting и видит актуальные данные по машинам.

**Система:**
- подключение через API-токен (сервисный пользователь);
- синхронизация: координаты, скорость, пробег, (опционально) топливо;
- health статуса интеграции;
- если Wialon только в LAN — VPN или sync-агент на стороне клиента (инфра-задача пилота).

**Приёмка:**
- [ ] Аккаунт Wialon привязан к org
- [ ] 6/6 unit сопоставлены с машинами FleetPilot
- [ ] Координаты обновляются не реже чем раз в 5 минут (цель MVP; идеал 30–60 сек)
- [ ] Падение API Wialon → статус Error + сообщение, без падения всего кабинета

**Статус:** 🟡 адаптер под пилот (нужен live Wialon); Omnicomm/СтавТРЭК — Should/Could, не блокер пилота #1.

---

### M4. Карта автопарка в реальном времени

**Задача:** диспетчер открывает карту и за секунды понимает, где машины и какой статус.

**Система:**
- карта со всеми активными ТС;
- статусы: в движении / стоянка / оффлайн;
- фильтр по статусу / машине.

**Приёмка:**
- [ ] Все активные машины с координатами на карте
- [ ] Оффлайн > N минут помечается отдельно
- [ ] Нет критичных ошибок при обновлении списка

**Статус:** 🟡 wireframes есть; web-карта — довести под live Wialon.

---

### M5. Заявки из ТрансМенеджер (чтение)

**Задача:** диспетчер видит заявки из своей TMS в FleetPilot без ручного копирования.

**Система:**
- коннектор: REST **или** файл/XML/ODBC каждые ≤15 мин (fallback, если нет API);
- поля: номер, А→Б, габариты/груз (если есть), назначенное ТС, статус;
- список заявок в UI с фильтром по статусу.

**Приёмка:**
- [ ] Новая заявка в ТМ появляется в FleetPilot ≤15 мин
- [ ] Ключевые поля читаемы
- [ ] Ошибка синка пишется в лог интеграции, UI не «молча ломается»

**Статус:** 🔴 не реализовано (P0 пилота).

---

### M6. Permit Agent — анализ маршрута и HITL

**Задача:** диспетчер негабарита вводит А→Б и габариты груза → система говорит, нужно ли спецразрешение, сохраняет заявку, диспетчер утверждает.

**Система:**
- rule-based анализ (длина/ширина/высота/масса/оси);
- создание `permit_request` + audit log;
- утверждение диспетчером (human-in-the-loop);
- проверка разрешения по номеру + госномер (реестр / DEMO stub → live parser API).

**Приёмка:**
- [ ] Analyze → `permit_required` корректен на тестовых габаритах
- [ ] Approve меняет статус на `approved`, пишет audit
- [ ] RBAC: только admin / dispatcher / fleet_manager
- [ ] 5 реальных/исторических маршрутов пилота пройдены end-to-end

**Статус:** ✅ API Sprint 7 (rule-based + stub Росдор); 🟡 UI диспетчера; 🔴 live parser API.

---

### M7. Fuel Agent — baseline и алерты

**Задача:** руководитель видит подозрительный слив / перерасход и экономию vs baseline.

**Система:**
- baseline расхода по данным телематики (история ≥1 мес, лучше 3);
- алерты: слив, перерасход vs baseline, (опционально) холостой ход;
- в MVP — правило + ручная верификация 2–3 алертов в неделю (не «чёрный ML»).

**Приёмка:**
- [ ] Baseline посчитан для машин с датчиком топлива
- [ ] Алерт появляется в UI / списке
- [ ] Ложный алерт можно закрыть / acknowledge

**Статус:** 🟡 модели `fuel_alerts` + seed; live-пайплайн от Wialon — довести.

---

### M8. ROI / P&L dashboard

**Задача:** комдиректор видит, сколько автопарк экономит и какие машины «в минусе».

**Система:**
- суммарная экономия ₽/мес (North Star);
- breakdown по категориям (fuel / route / dispatch / maintenance / permit);
- простая P&L по машине: доход / расход / маржа (ручной ввод или CSV из 1С в пилоте).

**Приёмка:**
- [ ] Dashboard открывается авторизованным пользователем
- [ ] Цифры за период согласованы с seed/пилотными данными
- [ ] Экспорт или скрин для отчёта пилота возможен

**Статус:** ✅ analytics API + KPI cards; 🟡 полноценный P&L per vehicle UI.

---

### M9. 1С — сверка затрат (CSV)

**Задача:** не заставлять бухгалтерию ставить HTTP API в пилоте; сверять топливо/расходы раз в неделю.

**Система:**
- шаблон CSV (машина, период, сумма, статья);
- импорт / ручная сверка с Fuel / ROI;
- полный API 1С — **вне MVP**.

**Приёмка:**
- [ ] Один успешный цикл импорта за пилот
- [ ] Расхождения видны (лог / таблица)

**Статус:** 🔴 формат + процесс (не полноценный коннектор).

---

### M10. Онбординг пилота (процесс, не «фича ради фичи»)

**Задача:** за 1 неделю получить доступы, baseline KPI, обучить диспетчера.

**Система / процесс:**
- NDA + 152-ФЗ;
- kickoff;
- обучение 2 ч;
- weekly status.

**Приёмка:** см. `PM-PLAYBOOK.md` фазы 3–4.

**Статус:** 📄 процесс описан.

| ЮKassa / биллинг в пилоте | Пилот — Founding вручную; биллинг после paid |

| Enterprise ML маршрутов (OR-Tools + LLM) | На 6 ТС нет данных; rule + HITL достаточно |

| Маркетплейс аренды, сложный multi-currency accounting | Не ICP пилота |
| Public API для партнёров | Нет спроса до 3+ клиентов |

## 5. Главные пользовательские сценарии (flows)

### Flow A — «Открыл кабинет → увидел парк» (activation)

1. Admin логинится  
2. Подключает Wialon / маппит 6 ТС  
3. Открывает карту → машины на местах  
4. Открывает ROI → видит цифры  

**Успех активации:** шаги 2–4 за первую неделю пилота.

### Flow B — «Заявка из ТМ → решение»

1. В ТМ создаётся заявка  
2. Появляется в списке FleetPilot  
3. Диспетчер смотрит ТС на карте / availability  
4. (Опционально) Dispatch suggest — **Should**, не Must  

### Flow C — «Негабарит → разрешение» (дифференциатор)

1. Диспетчер берёт заявку с габаритами  
2. Analyze-route → риск / нужность разрешения  
3. Утверждает (HITL)  
4. Проверяет номер в реестре  
5. Время vs baseline фиксируется для отчёта  

### Flow D — «Топливо → алерт → действие»

1. Wialon отдаёт топливные данные  
2. Система детектит аномалию  
3. Fleet Manager видит алерт  
4. Acknowledge / разбор

## 7. Интеграции (контракт MVP)

| Система | Направление | MVP-минимум | Fallback |
|---------|-------------|-------------|----------|
| **Wialon** | ← FleetPilot | token, units, position, odometer, fuel | CSV/ручной импорт координат недопустим как основной; VPN обязателен при Local |
| **ТрансМенеджер** | ← FleetPilot | заявки read | XML/файл ≤15 мин |
| **Росдор** | ←→ | analyze (rules) + check реестра | DEMO stub до ключа parser API |
| **1С** | ← FleetPilot | CSV затрат | ручная таблица Excel |
| **Yandex Maps** | ← | карта/геокод (если нужно) | статичная карта / Leaflet без routing |
| **Email** | → | логин, алерты (базово) | Telegram later |

Все запросы к внешним системам: **audit log**, credentials encrypted, данные в РФ (152-ФЗ).
